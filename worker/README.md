# Mood Engine, live

The Mood Engine addon as a small Cloudflare Worker. The nightly build still decides **what** is worth watching (your taste, your lists, your friends, the guard that keeps seen films out). The Worker only decides **how it is shown**: it reads what the build published and lets Stremio combine it.

What it adds to the static addon:

| | Static addon (v2) | Live (this Worker) |
|---|---|---|
| Board | 20 rows (v2.4) | the same rows, from the same build (20 with the index published on 11/10/2026), **plus My series**, a series row (see below) |
| Moods | pick a mood | pick a mood **and** a decade, a runtime, a country, a rating |
| Lists, Lists (unseen), Friends | pick a list / a friend | the same, **and** the four menus on top |
| By decade, By runtime… | four separate catalogs, 60 films each | one **Explore** catalog with all four menus at once, any order, all films |
| Search | none | **Search** in Stremio's search bar: title, director, mood, list, country, decade, length, friend |

Why a Worker at all: Stremio puts the menu you touched last in front of the others (`decade=1990s&genre=Nocturnal`, then `genre=Nocturnal&decade=1990s`), so a static host would need a file for every order of every combination. The Worker reads the extras in any order and filters on the spot.

**With Will's intake API off (the default: `WILL_UPLOAD_ENABLED = "false"` in `wrangler.toml`, see below), it has no accounts of yours and writes nothing about films**: the one thing it writes is the optional Workers KV namespace `SUBS`, and only for the subtitles the official list lacks on the private address (a download costs 2 writes and 1 delete since 19/10/2026, the day's counter being the second write; a failed download or a login that fails 1 write, a renewed login token 1 write about once a day; see Subtitles, measured in `test/subfile.test.js`). It has four optional secrets about OpenSubtitles (the API key; Marco's user name and password; and `SUBTITLES_PRIVATE_TOKEN`, which makes the private address `/k/<token>/` and signs the `/subfile` addresses). Everything it says about films is already in the public files the build puts on GitHub Pages; the subtitles come from OpenSubtitles; the My series row is the one thing bundled in the Worker itself (`src/series-list.js`, 85 titles, and the weekly rotation in `src/series.js`; no star ratings).

**With Will's intake API on** (a separate surface: `src/upload/api.js` answers EVERY path that starts with `/api/` before the addon sees it, `index.js`; the real routes are `/api/v1/friend-a/...` for the browser and `/api/internal/v1/friend-a/...` for the build, deploy and admin roles, and any other `/api/...` path is a JSON `NOT_FOUND` 404 of that API, even with the intake off, where main's addon would answer its own `{"err":"not found"}`; the two real prefixes answer 503 `CONFIG_MISSING` until every setting in the next section is made), the sentence above stops being true for that surface: the Worker then also stores, in the `WillState` Durable Object (SQLite-backed), invitation and credential hashes, the chunks of the ZIP being uploaded and normalized private snapshots of Will's data. Even then it does not parse the ZIP and does not run the film build inside the Worker; the build runs outside it.

SQL transactions reserve intake, consume an invitation, store immutable chunks,
claim a fenced six-hour lease, seal a candidate and promote the publication.
`complete` returns queued, never ready. Prepare is a durable barrier that blocks
a newer generation. ACK independently fetches the fixed release's exact receipt
and public person-context bytes, checks their registered hashes and identity,
then rechecks SQL state before promotion. Concurrent identical ACKs return 200
without another promotion. A later reconcile can complete a lost ACK; stale or
abandoned revisions cannot overwrite active state. Browser revocation preserves
accepted work, active input and public page.

Retention keeps active and previous private snapshots without TTL and one candidate,
with a 256 MiB reservation ceiling. The normal limit is three snapshots. Recovery
from an administratively abandoned preparation, a retryable failure after seal
before prepare, or an expired processing lease permits a fourth **transient** slot
only when active, previous and this request’s sealed source from an older lease
occupy the first three. The source must differ from active/previous. Allocation
and budget reservation are transactional. The source is removed only when its
replacement is sealed; active/previous are never removed by that cleanup. Repeated
abandonment/retry does not accumulate slots; restart retains the source and a new
lease discards an incomplete replacement. Old lease writes remain rejected, the
three-attempt processing ceiling remains, and a fifth snapshot is refused. ZIP chunks are deleted after seal or expiry;
uploads expire in 24h and queued archives in 7 days. Before admitting new work,
cleanup deletes an unprotected sealed candidate whose request is terminal or
absent. Active/previous, pending source and nonterminal prepared candidates remain
protected. Exhausting the three attempts therefore cannot strand the next request
behind an occupied snapshot slot. Storage failures return 503.

`GET /retained` (build role) returns only authenticated active/previous public
receipt descriptors and works without a processing lease. `GET /replay` returns
the prepared candidate descriptor plus its private request/snapshot IDs.
`GET /replay/:revision/blobs/:blobId/{manifest,chunks/:ordinal}` is read-only:
only the exact currently prepared, sealed candidate of Will is readable. Ordinary
blob routes and every write still require a valid processing lease. The same
strict repository, workflow, main ref, event and environment OIDC checks apply.

The private snapshot may be a version-1 gzip package with normalized inputs and
all exact release files, including rendered JPEGs. Stored bytes remain <=64 MiB;
expanded envelope is <=384 MiB, public file bytes <=256 MiB, <=30,002 package
entries, and normalized file bytes <=64 MiB. Paths use the public allowlist, have
no absolute/traversal components, and cannot repeat. Actual decoded sizes and
SHA-256 hashes are checked before writing; decompression has a hard output limit.
A package too large fails before preparation. Legacy normalized JSON is accepted
for ordinary refresh, but cannot replay a prepared publication without its bytes.
Prepared replay restores the original code/time/revision receipt without running
that code or accessing Will's sources. Missing public output allows replay;
mismatching output blocks reconciliation. Only verified public deployment is ACKed.

The existing admin workflow has `actions: read` and supports abandonment. Both CLI
and endpoint read only the fixed GitHub API URL for the original run and attempt,
with a 5-second timeout and 64 KiB response cap, no redirects. Completed status,
conclusion, run ID, attempt, code SHA, repository and workflow path must match.
The short-lived read token is never persisted or returned. Neither browser nor

## Put it online (one time, about 10 minutes)

You need a free Cloudflare account. No card is asked for the Workers free plan.

1. **Create the account** at <https://dash.cloudflare.com/sign-up> and confirm the e-mail.
2. **Install the tool.** In the repository folder:
   ```
   cd worker
   npm install
   ```
3. **Log in.** `npx wrangler login` opens the browser; click *Allow*.
4. **Check the address of the index.** Open `wrangler.toml`: `INDEX_URL` must be the address of your published `data/index.json`, e.g. `https://<your-username>.github.io/mood-engine/data/index.json`. (The pieces of the index are read from the same folder.)
5. **Deploy.** `npm run deploy`. The first time, Cloudflare asks you to choose a name for your `workers.dev` address; after that it prints the Worker's address:
   ```
   https://mood-engine.<your-subdomain>.workers.dev
   ```
6. **Look at it.** Open `https://mood-engine.<your-subdomain>.workers.dev/manifest.json` in the browser: you should see the addon's description with 25 catalogs. The Worker's home page (`/`) has the install link.
7. **Install in Stremio.** *Addons → paste* `https://mood-engine.<your-subdomain>.workers.dev/manifest.json`, or open `stremio://mood-engine.<your-subdomain>.workers.dev/manifest.json`.

The Worker's id is `com.mgusmao.moodengine.live` and the static addon's is `com.mgusmao.moodengine`, so they can be installed side by side. Both show the same Board rows, so installing both gives you the Board twice; keep one of them.

**After that you do not touch it.** The Worker re-reads the index every 30 minutes by itself, so the nightly build is enough. Deploy again only when something in `worker/` changes. Stremio reads the menus **when the addon is installed**: after a build that changes a menu (a country entering the top 12, a new friend, a new list), remove the addon and install it again.

**How the two swaps are read.**

- *Seen.* The build writes two **columns** on every row of every index file, `seenMask` and `wantMask`: bit *i* is `friends.people[i]` (the order of `config.json`), `1 << i`; a film two friends saw has two bits. They are derived from the film's `friends` column when the file is written; the build decoder checks exact agreement, including required cells omitted from a declared 29-column file. The Worker checks mask types and whether populated `friends` sections have nonzero masks; it does not recompute every bit. `select()` and `search()` take an optional `seen(film)`; the friends' routes hand in `(film) => (film.seenMask & bit) !== 0`; the friend is resolved by name in each piece’s own `friends.people`, so cached pieces from a different ordering keep the correct viewer. A piece missing that friend returns 503. Every other caller gets the film's own flag (Marco's), so the public address does not change by a byte. "Include seen" asks the same function.
- *Watchlist.* The build writes one piece per friend, `index-v2-row-watchlist-<friend>.json`: the films the friend has on the watchlist and has **not** seen, that the recommendation rule (`eligible`) lets through, in the order of the index (best rank first), at most 100 (`V2_ROW_MAX`), with the film's general text as the row's text. It is written for every friend, empty or not (a missing file is an outage, an empty one is an answer). The Worker reads **that** piece and nothing stands in for it: if it is missing, or declares another friend's `part`, the page is empty (30 s cache); the whole v2 index, which a missing slice normally falls back to, holds Marco's `watchlist` row, and so does the legacy Board.
- *An index with no masks* (every file published before 29/10/2026, or a piece cached from before) cannot serve a friend: **503, `Cache-Control: no-store`**, never the films with nothing seen. `hydrate()` says it (`index.masks`); the handler checks the menus and every page it cuts. A declared 29-column file with missing or invalid nonzero masks is also refused. Zero masks may legitimately be null or omitted at the end of a row when that section of `friends` is empty.

## What each request reads

The free plan gives a request **10 ms of CPU**, and a request that lands on a fresh isolate has to parse the file it reads before it answers. Parsing the whole index takes ~6 ms on its own, so the build also writes it in pieces, and each request reads only the piece it needs:

| Request | Reads | Size |
|---|---|---|

### The pieces of the Discover's calculated options (Marco, 29/10/2026)

Marco, 29/10/2026 (~18:1x UTC, questionnaire "peças de índice por opção do Discover"): every calculated option of the Discover (a genre, a region, a decade, a union of lists, a director's card: the ones whose films the build wrote as `ids`; the options of ONE list read `index-list-<id>.json` already) has a piece of its own, `data/index-v2-opt-<catalog>-<option>.json` (`encodeURIComponent` of both ids, joined by a hyphen, as the Board's row pieces do; `urls.opt(catalogId, optionId)` in `src/handler.js`). **Why:** a calculated option read the whole `index-v2.json` (9.4 MB of text), which costs 400 to 970 ms of CPU on a cold isolate of Cloudflare, measured on 29/10/2026 with the Genres option Drama: **971 ms** on the first read of an isolate, **405 ms** on the second, **15 ms** warm (the CPU of the free plan is 10 ms per request; Marco's session ceiling is 35 ms, judged on the figure after publication). The pieces are 45 to 359 KB (median 111,305 bytes).

**What the piece holds.** The envelope of every other v2 piece (`meta`, `moods`, `moodMenu`, `lists`, `rules`, `friends` and `directors` as labels, `discover` as labels with `ids: []`: what `rulesOf`, `includeSeen`, the chips of the card and `info()` need), plus in ITS option: `ids` = the first ids of the option (the build's order) and two numbers of the WHOLE option, `total` and `totalAll`; plus the films of those ids (the same rows as `index-v2.json`). A director's card also keeps its own "X loves" option of `directors.options` with its texts (the card reads them there). **Where the cut falls:** after the 300th film the default view SHOWS (not seen, and `recommendable` unless the option is `curated`), not after the 300th id: a film he has seen takes a place in `ids` and none on the screen, so a cut at the 300th id gave a short page 3 (`optionCut` in `lib/index-export.js`). An option that shows fewer than 300 is written whole. **Include seen:** it shows a superset of the default view in the same order, so the first 300 films of the default view are inside the first ids; the piece needs nothing else for it (a test puts a seen film and a film under the rule inside the ids). `total` is what the default view shows in the whole option and `totalAll` what "Include seen" shows: they are the `X-Total` of the answer, which the piece cannot count by itself.

**When the Worker reads it (updated 30/10/2026).** When the full v2 index is not fresh in memory, `completeOptionPage` first checks the piece identity, unique IMDb ids, exact film coverage and valid totals. It selects the option without filters and with Include seen; only when that count equals the build’s `totalAll` can the piece answer every filter and page for Marco or a configured friend. The original selection and pagination compute that viewer’s total. This relies on truthful totals from the verified build: a falsified total that hides missing candidates cannot be detected from the piece alone.

A partial piece keeps `optionPage` for Marco without additional filters: it must fill the requested page or reach the declared total. Friends, filtered partial pieces, unavailable or incompatible pieces fall back to `index-v2.json`. The prefix path cannot detect an inflated declared total on a page it can fill; `verify.js` recomputes totals against the full index. Neither path uses option pieces for Will’s independent publication.

The piece remains an optimisation: its network deadline is 2 s (`OPTION_PIECE_TIMEOUT_MS`), and the full index already fresh in memory skips the fetch. Pieces share 12 memory slots and 48 MB with mood and list pieces. `X-Index-Source` describes the file used. For a friend, an otherwise fresh cache copy without compatible masks or friend identity gets one source refresh, shared and limited to once per URL per minute per isolate. Persistent incompatibility remains 503/no-store, with generation, age and source when available. This reproduces a transition defect; the historical live 503 lacks the response evidence needed to identify its cause.

**The build.** `lib/index-export.js` `optionPieces()` writes them after the other v2 files (which are untouched: an offline build of the caches of 28/10/2026 at 415bd4e and at this change gave 1,090 files byte for byte equal, `builtAt` aside, plus the new ones); the log says `Discover option pieces: N files, M MB`. The name has to be one the public files allow (lower case words and hyphens after `index-v2-`: `lib/learning/public.js`), or the build stops naming the option; two options cannot write one file. `verify.js` checks every piece (exactly the films of its first ids, the option's ids and its two totals recomputed from the whole index, the menus of the whole index everywhere else) and refuses an `index-v2-opt-*` file the index does not account for. Measured on the offline build of that day: **168 files, 24.7 MB of text (8.5 MB gzipped), 27,924 film rows in all (17,572,432 bytes at 629 a row), the largest piece 488 films**; the other 7.1 MB is the envelope, 39,708 to 58,767 bytes in each file (39,533 to 57,866 without the option's own ids; the top is the cards of directors, which carry their "X loves" texts; the menus and the lists' names are the same in every one). The questionnaire's estimate, about 18 MB, was the rows alone.

**Measurements and limits.** The 29/10/2026 Node bench in BACKLOG is historical and does not approve the Cloudflare ceiling. On the public snapshot generated at `2026-10-30T00:09:00.750Z`, 122 of 168 options are complete and 46 are partial. ### The file format

`index.json` is one JSON object: the menus (`moods`, `lists` — `{ id, label, short?, popular, films }`, `short` from 22/10/2026 —, `friends`, `meta.countries`, `meta.decades`), the Board rows (`rows`: row id → IMDb ids, in the order the build calculated), and `films`: one **array per film**, columns named once in `cols`. Composite values are short delimited strings (`countries` = `"United States|France"`, `lists` = `"crit:5,cannes:1"`: list id, the position the list SHOWS the film in — the curator's, except for a list with `order: "rating"` in config.json, where it is the rank by Letterboxd average, 22/10/2026). Objects with nested arrays took twice as long to parse; `lib/index-rows.js` has the format and `decode()` turns a file back into the object form used by the tests and `verify.js`.

Per film: `tt name year decade runtime countries language lbRating tmdbRating tmdbVotes imdbRating seenBy wantBy friendsAvg taste quality rank poster desc genres director keywords moods lists friends watchlist seen find country` (`country`, 13/10/2026: the film's main country, written only when it is not the first of `countries`, for the facts line of a description; the By country filter reads `countries` alone). Since 23/10/2026 the main country is the director's country when she is a citizen of a producer or when the film is not in English and she is a citizen of a country that speaks its language, else TMDB's `origin_country`, else the language-and-producers rule (`lib/countries.js` `mainCountry`), so `country` is written for 271 films of the index of 23/10/2026 (205 of the unseen eligible ones; 30 before): Roma reads Mexico on its card and in the Latin America row, but `hasCountry` (`src/film.js`) does not find it under Mexico, because Mexico is no producer. NOT changed here (the Worker is not published by this work): the proposal in BACKLOG.md of 23/10/2026 is that `hasCountry` also reads `country`. A column that is empty means *not known*, never a guess: a film with no runtime matches no runtime menu. `find` is the text a search reads, already lower-cased and without accents.

The v2.1 columns: `imdbRating` (IMDb's dataset), `seenBy` and `wantBy` (how many of the **51 people you follow** saw the film, and how many have it saved and have not seen it), `friendsAvg` (the average of those who saw and rated it, one decimal) and `poster` (the cover with the ratings drawn on it; only the films the static files show have one, the others use the same poster service as the static addon). `friends` is something else: the 4 configured friends **by name**, which is what "gustavo loved" and the Friends catalog read.

`desc` is the film's description WITHOUT its first line (description v3, Marco, 20/10/2026, lib/describe.js `liveDescription`): `<the first three actors>\n<line 2>`, `meta.separator` (config.json → `descriptionSeparator`) and the synopsis; line 2 of a film's general text is `Mood: <the mood the film fits best> · <up to three genres> · <up to three keywords>.` (the keywords are the film's mood words, up to four, an initial capital each, from the build's `descWords` (the words of every mood of config.json, 30 today, cleaned of a word inside another); the Worker shows three; never TMDB's raw keywords: Marco, 20/10/2026. In the v2 index the `keywords` column is another list, the search's). The two card lines are positional (an empty first line when the film has no actors; no line 2, the actors alone). A film with no credits, no genres and no synopsis (22/10/2026: East of Eden 2026, `tt21097264`, no TMDB record, the one empty card of the 1,331 on the 20 Board rows; since 22/10/2026 ~06:40 UTC the build keeps a film with no TMDB record of its own out of the rows, so no Board row holds that card any more; the parity stays for any film with no credits, no genres and no synopsis, and the tests use a bare item) has `description: ""` in the Worker as in the static addon, the key present, never left out (`toMeta` returns the string as `compose()` made it; `test/parity.test.js` "a film with no credits, no genres and no synopsis" compares the two, and `test/real-index.test.js` does it film by film). `toMeta` (`src/meta.js`) builds **line 1** from the columns (`director`, `runtime`) and the actors of `desc` (`Akira Kurosawa · 2h22 · Toshirō Mifune, Tatsuya Nakadai, Kyōko Kagawa.`; no country, year or ★) with `creditsLine`, the same function as the build's, cut at 80 characters AFTER it is built (three actors, then two, never fewer than two when the cast has them: Marco, 21/10/2026 ~15:00 UTC, D4; `test/parity.test.js` compares it with the build's over every combination of the test's directors, casts and durations). ### Which films are recommended (Marco's rule of 10/10/2026)

A film is recommended only if the **unrounded Letterboxd average** of its IMDb identity is **3.5 or more, OR a configured friend's own rating is 3.5 or more, OR it is vouched for** — in a critic or director list (config.json `trust`; a fan list does not count) or loved by one of Marco's favourite directors through a high or medium source (`data/directors-loved.json`) — **and, when it has a Letterboxd average, that average is 2.5 or more** (Marco, 11/10/2026: the exception's own floor, `VOUCHED_MIN_STARS`). The build decides this once per film (`lib/recommendation-quality.js`) and writes it in the index as the flag **`eligible`**; the Worker reads the flag and never recomputes the rule. A film with no Letterboxd average and no friend's rating is **not** eligible unless it is vouched for: TMDB, your own rating, "watched" and "on the watchlist" never stand in for either. (Crowd averages of the 51 people you follow do not count as the friend exception; only the configured friends do.)

The flag is used by everything the Worker assembles from the pool: **Explore, Search, Moods**, and every combination of the decade, runtime, country and rating menus with them (the rating menu too: "Under 3.8" shows the films of that band that pass the rule). It is **not** applied to the Board rows (the build already filtered them and the Worker serves them as built), **Lists**, **Lists (unseen)** and **Friends** (direct curator and friend collections: their content and order are untouched). Filtering keeps the order of the survivors and fills no gap: a page is the first 100 eligible films of the catalog's own order, and `skip` counts eligible films.

**The music rule (Marco, 22/10/2026 ~06:40 UTC: "extend rule D to all the rows of the Board and to the cuts by country and decade").** The build marks a music film he has not seen and has no evidence for (lib/pool.js `musicGate`: a director he rated in 2 films or an artist in 3, his watchlist, a critics' or directors' list) with **bit 8 of the film's `flags`** (`musicOut`, true or absent; lib/index-rows.js, lib/index-export.js, checked by lib/index-validation.js: never on a film marked seen). The film **stays `eligible`**. The Worker serves what RECOMMENDS from `recommendable` = `eligible` and not `musicOut` (`src/film.js`): **Moods and Explore, with the decade, runtime, country and rating menus on top** (`RECOMMENDING` in `src/catalogs.js`), and the profiles' **Tonight, Under 100 min and themes** (`src/profiles.js`). **Search** answers to country, decade, genre, keyword and mood words as well, which is a cut like the menus (measured on the real index of 22/10/2026: `korean` brought 11 held-back films in the first 100, `south korea 2020s` 10 of 27, `concert` 82 of 100, `music documentary` 70 of 100), so a held-back film is found there **only by its title** (`src/search.js`: every word of the search is a word of the title; "bts", "taylor swift", "arena tour" find it, "korean" does not) and only while it is `eligible`. *A reading of the session, to confirm with Marco; if asking for a film by a word that is not in its title should find it too, the rule is one line in `search.js`.* It is **not** applied to **Lists, Lists (unseen), Friends, Loved by directors**, the **Board rows** (the build filtered them), the profiles' **Watchlist** (a film on it is its own evidence) and the curators' rows (Closet, Who vouches). **Fallback:** an index without the bit (built before, or with `music.needsEvidence` off) makes `recommendable` equal `eligible`, so the Worker behaves exactly as before; the field is optional and bit 8 means nothing to a Worker that does not know it (it reads bits 1, 2 and 4). Tested in `test/music-rule.test.js` (a small world: the show leaves Moods, Explore and every menu, the profile rows, the page counts and the searches by country, decade, genre and keyword; it stays in a search by its title, Lists, Friends, a Board row, the watchlist and the curators' rows; an index without the bit serves it) and against the real index in `test/real-index.test.js` (five films, static addon and Worker side by side).

## Subtitles

The addon also answers Stremio's `subtitles` requests (`/subtitles/{movie|series}/{tt…}/{extras}.json`, extras `videoHash`, `videoSize`, `filename` in any order, an episode id is `tt0944947:1:1`). It does not host or convert anything: the list comes from the **official OpenSubtitles addon** (`opensubtitles-v3.strem.io`), only English (`eng`) and Portuguese (`por`, `pob`, and the `pt-br`/`pt-pt` spellings), re-ordered by how well each subtitle fits **the file that is playing**, at most **15 a language**, ids prefixed `moodsubs-`:

**Limits on the official list (13/10/2026; before that its fetch had none).** The request has **10 seconds** over the whole of it (the body included) and the body is read up to **2 MB** (a declared length over that is refused unread, an undeclared one is cancelled at the limit), the way the hash search already was (3 s, 1.5 MB). It is made only on an allowed host (`SOURCE_HOSTS` in `src/subtitles-source.js`: `opensubtitles-v3.strem.io`, exactly), over https, with no credentials and port 443 or none. A `SUBTITLES_SOURCE` setting that names any other host (`opensubtitles-v3.strem.io.evil.example`, `https://127.0.0.1`), another scheme (`http://`, `ftp://`), or a text the URL parser reads as another host than the one written (a user name in front of another host, `https://evil.example?@opensubtitles-v3.strem.io`, `#@`, `%2E`, full-width dots, a tab) is refused with `unexpected source host`, with no request sent. So the setting can no longer point at a mirror on another host: to allow one, add it to `SOURCE_HOSTS`. A failure of any of these is the same as the source being down: the copy up to a day old is served, else the answer has no subtitles. Tested in `test/subtitles.test.js` with fake fetches; nothing here was measured against the real addon.

| Tier | Meaning | Shown as |
|---|---|---|
| exact | OpenSubtitles says the subtitle belongs to a file with this very hash (needs the API key below; **only on the private address since 19/10/2026**, see "The hash search is private") | `English 1 ✓ · BluRay · AMIABLE` |
| same release | its release group is the file's (`-AMIABLE`, `[EtHD]`, `x265-RARBG`, any case), **or** it has the same source (BluRay / WEB-DL / WEBRip / HDTV) **and** the same resolution as the file | `English 2 ≈ · BluRay · AMIABLE` |
| the others | the official order | `English 3 · WEB-DL · FGT` (the language and position, then available source/group) |

Portuguese rows use the short names `PT-BR` and `PT-PT`, with the same numbering and marks: `PT-BR 1 ✓ · BluRay · AMIABLE`, `PT-PT 1 ≈ · BluRay · AMIABLE`, `PT-PT 2`. Numbering restarts per language; missing release details are omitted. Without the key the exact tier simply does not exist; nothing fails.

**How the tier is shown.** Stremio groups its language menu by `lang`, and a `lang` it does not know becomes a menu entry of its own (stremio-web `SubtitlesMenu.js`, `languages.label()` returns the string itself): custom text there would split English into one menu entry per tier. So the tier never goes in `lang` (which was the official addon's own code until 14/11/2026 and is, since then and for every app, ONE name of the addon's own for each language, the same for every tier: see "`lang` is a language name of the addon's own, for every app" below), and the tier goes in **`label`**, which the SDK documents ("label shown in the subtitle picker instead of the language name"), which stremio-core keeps (`Subtitles { id, lang, url, label, fonts }`) and which stremio-web's `SubtitleVariant` shows on the row when it is not empty and does not start with `http`. I read that in the `development` branches on 10/10/2026. **Not checked on a device:** a Stremio app built before `label` was supported would show just the language name on each row (the order is still right, only the marks are missing).

**The `label` starts with language + alternative number (Marco, 30/10/2026).** `English 1 ✓ · BluRay · AMIABLE`, `English 2 ≈ · WEB-DL · FGT`, `PT-BR 1 · BluRay`. Each language is numbered after the existing filtering, deduplication, stable tier ordering and cap of 15; the number is a position in this response, not an identity or a synchronization score. The source and group replace the full film title, and appear for marked choices too. With no metadata the label is `English 1` (or `English 1 ✓` when the source associates the hash). Known sources are BluRay, WEB-DL, WEBRip, HDTV and display-only DVD/DVDRip; this does not extend the matching rules. Group text is one line, without control/direction characters, limited to 24 Unicode code points including an ellipsis. The same `shape()`/`labelOf()` path covers public/private addresses, signed `/subfile` extras and series. IDs, URLs, `lang`, language policy, matching and sorting are unchanged.

### Which languages are listed (Marco, 10/10/2026: original audio + English subtitle; Portuguese only for a film in Portuguese)

The list above is not always English first. The film's **original language** (the index's `language` column, an ISO 639-1 code from TMDB) decides which languages are listed and in what order:

| The film's original language | Listed, in this order |
|---|---|
| Portuguese (`pt`) | Português (BR), Português (PT), English |
| any other known language (`sv`, `fr`, `ja`, `en`…) | English only. If the official list has **no English** for that film, the Portuguese ones instead (better than nothing) |
| not known: an episode or any series id, a film that is not in `film-languages.json`, no language written for it, TMDB's `xx` ("no spoken language"), or the file cannot be read | English, Português (BR), Português (PT): the order before this rule |

The tiers, the labels, the 15 a language and the `moodsubs-` ids are unchanged by this rule, and this rule does not decide what `lang` says: since 14/11/2026 it is the language's own name, for every app (see "`lang` is a language name of the addon's own, for every app" below); the order of the languages is the one this rule gives. The rule is `languagesFor()` in `src/subtitles.js`; the answer says what it read in the header `X-Subtitles-Film-Language` (`pt`, `other` for any other real language, or `unknown`) and `X-Subtitles-Languages-File` (`ok`, `failed`, `paused` or `not-a-film`).

**Where the language comes from (updated 12/10/2026, approved by Marco).** The build publishes **`data/film-languages.json`** next to the index (`lib/index-export.js` `languagesFile()`, checked by `verify.js`): `{ "v": 1, "builtAt": "…", "pt": "|0111161|…|", "known": "|0050083|…|" }`. `pt` holds the films in Portuguese, `known` the films in any other real language; TMDB's `xx` ("no spoken language") and films with no language are in neither. The ids are the numbers of the IMDb ids, sorted, with a bar on both sides, so the whole lookup is one `String.includes("|0111161|")`. Measured on the published index of 12/10/2026 22:20 UTC (11,148 films): **87,323 bytes (33,138 gzipped)**, 317 `pt` + 10,465 `known`; `JSON.parse` takes **0.03 ms** (0.04 ms for the first parse and lookup in a fresh node process) and a lookup 0.002 ms, against the 40 to 50 ms the whole index costs on a fresh isolate. That is why `/subtitles` can read it on a cold isolate and is **deterministic**: the same film gets the same rule on every request.

The Worker fetches it the way it fetches the index (`src/film-languages.js`): the isolate's memory, then the Cache API (it does keep entries on this `workers.dev` address: see the measurement of 13/10/2026 under "The private address"), then the network; fresh for 30 minutes (like the index); when the read fails or times out the last good copy is served for up to 7 days (the one in this isolate's memory, or the Cache API's), and for the minute that follows nothing waits for the failing read again; the fetch skips the edge cache, so a 404 stored before the first publication is never read back as the file; it is asked **together with** the official list and the hash search, with a **1.5 s timeout**. Any failure with no older copy to fall back on (file missing, malformed, another `v`, too slow, network down) gives `unknown`, which is today's answer (English, Português (BR), Português (PT)), is logged as `film-languages-unavailable`, is not retried for a minute, and makes the answer "degraded": remembered 300 seconds instead of 3600. Subtitles never wait for it beyond the timeout and never fail because of it. The file exists on the published site only after the first build that writes it: merging this work to `main` starts that build at once (the workflow's push filter includes `lib/**` and `verify.js`), and until it has finished every film is `unknown`; publishing the Worker before that does no harm. An episode or any series id is never looked up.

**Evidence and limits.** Live index of 12/10/2026: 10,803 of 11,148 films have a language (the film-research count of the same day was 10,965 on an earlier build), 21 of them `xx`. Tests: `test/subtitles.test.js` (the rule alone, on the real list for Paterson, the file source with every failure, and the handler for another language, Portuguese, an episode, a cold isolate, a missing, malformed and slow file); `test/index-export.test.js` (the build's file and `verify.js`); `mutation.mjs` entries "film languages" and "subtitles 12/10 film language". **Not checked on a device:** no one has opened a subtitle menu on the TV, the Mac or the phone with this rule, so what a Stremio, Nuvio or Fusion app does with a list that has only English rows is not known.

### Subtitles the official list lacks, on a private address (Marco, 12/10/2026: use his OpenSubtitles account, only on an address he installs)

The official addon's list misses some of the subtitles OpenSubtitles says were made for the playing file (Paterson, `tt5247022`: of the three hash matches, the official list had one). On a **private address** the hash search (one request, cached 24 hours; since 19/10/2026 it runs only there, see "The hash search is private") also collects those matches, and the ones the official list does not have join the **exact tier** in their language. The public address makes no hash search (the official list alone, ordered by the file's name) and **never lists a `/subfile` address** (`test/subfile.test.js`).

**The hash search is private (W4, Marco's decision of 19/10/2026).** The REST search by the file's hash, the one that spends the OpenSubtitles account's quota and gives the `✓ exact` tier and the extra rows, is made **only** for a request that came in under a valid `/k/<token>/` prefix. On the public address and on the public profile addresses `/p/<profile>/` the answer to `/subtitles/…` is the official list alone, ordered by the file's name (same release, then source and resolution), with no `✓ exact` mark, no call to `api.opensubtitles.com` and nothing about the hash in any event the Worker logs (and Cloudflare's own invocation log, which would record the whole address, hash included, is switched off in `wrangler.toml`, see "Which build is running, and the logs"); the header `X-Subtitles-Exact` says `public` there (`no-key` is now only for the private address without the API key). What guards it is the flag the handler sets after the token in the prefix has been compared in full with `SUBTITLES_PRIVATE_TOKEN` (`src/handler.js`, `exactSearch`), not text in the address: `/k/` in a query string, or a prefix with a wrong token (a 404 before anything else), never lets the search through. Under `/k/<token>/p/<profile>/` the request is private, so the search is made. **Effect on the six Nuvio profiles:** the manifest of every profile (`buildProfileManifest`, `src/manifest.js`) announces the `subtitles` resource for movies and series, and its description used to say "Also English and Portuguese subtitles, the ones made for your file first". A profile installed at `/p/<profile>/manifest.json` therefore keeps the official English and Portuguese list (same file name first) but **loses the exact tier**. The description of the six profiles now says "Also English and Portuguese subtitles: the official list, and the ones made for your file first only on the private address." (one sentence for both addresses, because the manifest under `/k/<token>/` is byte for byte the public one, tested; `test/profiles.test.js`). **The main manifest `/manifest.json` says the same sentence since 19/10/2026 (Marco's decision, questionnaire)**: before it carried the old one, which on the public address was no longer true for it either. `test/fixtures/manifest-3.3.0.json` and `legacy-manifest.json` were regenerated with that one sentence and nothing else (the diff is three insertions: ": the official list", " and", " only on the private address"); the version stays 3.3.0, because the sentence is not a product change and no test ties the version to the text. A client that installed the main address keeps the old text until the addon is reinstalled over the same address. A client that installs `/k/<token>/p/<profile>/manifest.json` keeps both, at the cost of a token in its addon collection (see below). Tested in `test/subfile.test.js` (the six profiles, the public address, `/k/` text that is not a token, a wrong token) with mutations in `mutation.mjs` (`W4:`).

**The private address.** `https://<this Worker>/k/<SUBTITLES_PRIVATE_TOKEN>/manifest.json`. A prefix `/k/<token>/` in front of **any** existing path (the manifest, a catalog, a profile `/p/<profile>/…`, subtitles, the home page) is served exactly like the same path without it: the manifest is byte for byte the public one (tested). A wrong, short, long or absent token, or a Worker with no `SUBTITLES_PRIVATE_TOKEN`, is a 404 that says nothing about why; the token is compared by hashing both sides and comparing every byte. Only requests under a valid prefix get the extra rows. Install the private manifest **instead of** the public one in Stremio and Fusion, not next to it: two addons that both answer `moodsubs-…` ids would show two lists, and stremio-web keeps the first entry per id. The install page under the prefix links to the private manifest. **Treat the private manifest URL as a secret of the same kind as a configured Torrentio URL.** The token is in that address, so it is shown on the private install page, it is stored in the client's addon collection (which Stremio synchronises across devices and accounts' backups), and it appears in Cloudflare's request logs (`wrangler tail`, the dashboard logs): anyone who can read the addon collection or those logs can read the token. Every answer under the prefix is `Cache-Control: private` and `Referrer-Policy: no-referrer` (also the OPTIONS answer and the 405), so a shared cache does not keep it and a page it opens does not hear of it. **Rotating or deleting the token makes the whole addon answer 404 on every device** (the catalogs and the profiles too, not only the subtitles) until the addon is removed and installed again under the new address; the public address is unaffected.

**Which rows, in what order.** Left out: AI-translated and machine-translated subtitles (when the search says so), languages other than English and Portuguese, subtitles in several parts (CD1/CD2), and any result with no id to compare with the official list. The rest join the exact tier **after the official exact ones and before the same-release ones**, so an app that takes the first subtitle of its language gets an official exact one **when the official list has one in that language**. **When it has none, the extra leads its language and is what such an app picks by itself, and opening it costs one of the day's 20 downloads**: the guard is that the rows are hidden whenever the state says opening them would fail (below), not that they are never first. **That is how it was while `lang` was the language's code, and how it is again with the switch off.** Since the code of 14/11/2026 these rows, like the official ones, go out to every app under a language name instead of the code (see "`lang` is a language name of the addon's own, for every app" above); that is what the code does. **What an app that picks by language code is EXPECTED to do with that, and is NOT VERIFIED:** pick none of this addon's rows by itself, in which case the quota of 20 would be spent only when a row is picked by hand. The expectation rests on the reading of stremio-web's code (its automatic choice matches language codes only) and on the comment of a member of the Stremio organisation in `stremio-features#1551` (21/01/2026); the Samsung app, the reason for the change, is closed, and the Worker in production does none of this until it is published. The proof is on the TV, after the publication. The order of the rows is unchanged. The film's language rule above applies to them and the 15 a language cap counts them. Label `English ✓ exact` (or `PT-BR ✓ exact`, `PT-PT ✓ exact`; before 13/10/2026 it was `✓ Exact · <release>`), id **`moodsubs-os<file_id>`** (the same file always gets the same id), address `https://<this Worker>/subfile/<file_id>/<exp>/<sig>.srt` (the address does not carry the private token; `exp` is when it stops working, see "The signature"). The header `X-Subtitles-Extras` says how many were added, or why none (`off-quota`, `off-login-paused`, `off-failing`, `off-kv-timeout`, `off-error`). **The rows are not listed at all while the day's quota is out (also right after a download that left none), a failed login is being waited out, the last 3 downloads failed, or the KV did not answer within 300 ms**; such an answer is "degraded" and is remembered 300 seconds (body `cacheMaxAge` and `Cache-Control` alike) instead of 3600, as is any answer, on either address, whose film language could not be read or whose hash search failed or is paused. A row Stremio already holds can still outlive the state that hid the others, for up to an hour.

**Secrets and the KV binding.** Four secrets, all optional; without all of them (and the key) nothing changes: no extra rows, and `/subfile` is a 404.

```
npx wrangler secret put OPENSUBTITLES_USERNAME      # the OpenSubtitles user name, not the e-mail address (the Jellyfin plugin reports a 400 at login with the address)
npx wrangler secret put OPENSUBTITLES_PASSWORD
npx wrangler secret put SUBTITLES_PRIVATE_TOKEN     # 16 to 128 letters, digits, "-" or "_"
```

Plus the key `OPENSUBTITLES_API_KEY` of the section below, and the **KV namespace `SUBS`** declared in `wrangler.toml` (`[[kv_namespaces]]`, binding `SUBS`; the namespace id is not a secret). What must outlive an isolate and be shared by all of them is in KV (the Cache API turned out to keep entries on `workers.dev` too, measured 13/10/2026, but it is per data centre and may evict at any time): `srt:<file_id>` the subtitle (30 days), `token:v1` the login token (about 20 hours; one fixed key, never made from the credentials), `quota:v1` when the quota comes back, `os:remaining:<yyyy-mm-dd>` the day's counter (19/10/2026: `{ remaining, until }` written after every download answer that carries `remaining`, under the UTC date of the window the answer closes, that is the date of the moment just before `reset_time_utc`, or today's date when the answer gives no reset moment, in which case `until` is the next midnight UTC; it lives until `until`; the next download reads today's key and tomorrow's, because a window can end after midnight), `loginfail:v1` a stamp for a failed login (10 minutes), `health:v1` how many downloads in a row failed (forgotten after an hour). Without the binding the same things live in each isolate's memory: nothing breaks, a cold isolate just starts again and may log in again (the login is limited to 30 an hour). A KV read or write that fails is logged as `subs-kv-failed` (the operation and a fixed label, never the key or the value) and never fails the request. Workers KV on the free plan has daily limits on writes (Cloudflare documents 1,000 a day; I did not re-check it today): the writes here are, measured in `test/subfile.test.js`: a download that works is 2 writes (the day's counter `os:remaining:<date>`, which is new since 19/10/2026, and the subtitle) and 1 delete (the failure count cleared), plus 1 write when it had to log in (the token, about once a day); an answer that carries no `remaining` writes no counter; a download that fails is 1 write; a spent quota or a failed login is 1 write; a subtitle already kept, `HEAD`, a listing and everything on the public address write nothing. The 20-a-day OpenSubtitles quota keeps the writes of a working service far under any such limit; **while OpenSubtitles is failing (429, 5xx or the network; a 5xx carries no `remaining`) it does not, so since 19/10/2026 `download()` stops asking and writing once 3 downloads in a row have failed for those reasons** (`busy`, `download-failed`; the count is forgotten after an hour without news, then 3 more are tried): before that, a signed address opened again and again cost one call and one KV write each (measured by the security review, 50 requests = 51 writes), and the 3-in-a-row count only hid the rows. A row opened while the run stands is a 502 `busy` that asks nobody; a recovery inside the hour is not noticed until it is over. **A bad file does not count for this stop** (`no-link`, `file-failed`, `bad-file`: no link, a page instead of a subtitle): those failures still count, with the others, for hiding the rows (3 of any kind), but another file opens as usual; `health:v1` holds both counts, `{ fails, service, at }` (re-review, 19/10/2026: after the first version of the stop, one bad file that Stremio retried by itself made every file `busy` for an hour). A KV read that does not answer within 300 ms when the rows are being listed means no rows that time (logged as `subs-kv-slow`).

**The signature and its expiry (13/10/2026; before that an address never expired).** `exp` is a moment in epoch seconds (10 digits): **30 days from the day the row was listed, rounded up to the day** (the same 30 days the subtitle is kept in KV), so an address is the same all day long and a cache can keep it. `sig` is the first 16 hex digits of HMAC-SHA256 of `<file_id>`, a line break and `<exp>`, with a key derived from `SUBTITLES_PRIVATE_TOKEN` (SHA-256 of the domain label `mood-engine/subfile/v3`, a NUL byte (`\0`) and the token) and **never from the OpenSubtitles password**; changing the password changes nothing here, changing the token changes every address. The expiry is signed, so it cannot be moved; an `exp` already past, or a signature that is not for this file and this `exp`, is a 404 before anything else happens (compared in full whatever the first difference). A row Stremio keeps for longer than that stops opening and comes back with a new address the next time the title's subtitles are listed. What it guarantees: whoever does not hold the private address, nor a row it handed out, cannot make the Worker spend the quota on an id of their choosing, and a row handed out cannot be used after its `exp`. What it does not: a row is still a bearer address, anyone who sees it (Stremio, its logs, a screen share) can open that one file until `exp` (or until the token changes), and each such file costs one of the 20 downloads the first time; and a copy of the answer in a shared cache (`Cache-Control: public, max-age=86400`) may be served up to a day after `exp` (not measured). **The address without `exp`, `/subfile/<file_id>/<sig>.srt`** (signature of the file id alone, domain label `v2`), is a 404. It was issued until 13/10/2026 and accepted for 30 more days, until 2026-11-13T00:00Z (Marco did not fix those 30 days, the choice was the session's of 13/10/2026); on 14/11/2026 the code that checked it was removed from `src/subfile.js` (the constant `V2_ACCEPT_UNTIL`, `signFile`, `verifySig`, the `v2` key label and the optional group of the path), which changed no answer: the form was already a 404 by its date, and now the path does not match at all (the same request to the code of `origin/main` `92187a6` and to the code without the form, on 14/11/2026: without `exp` 404 and 404, with `exp` 200 and 200). The label `v2` is not to be reused for another key. Tested in `test/subfile.test.js` with the clock injected: an address listed today answers 200 and the same one 31 days later 404, both sides of the exact second of `exp`, and the address without `exp`, signed in the test with `node:crypto` exactly as it used to be, a 404 at five moments (before, at and after the old date) with the subtitle kept and no call to OpenSubtitles.

**What `/subfile` does.** It checks the signature and the expiry first (404 before OpenSubtitles is asked anything), then looks for the subtitle kept in memory or KV, else does `POST /login` (one login at a time per isolate; KV is read first, so a cold isolate uses the token another one stored and does not repeat a login that failed), `POST /download` with `{ file_id }`, and a `GET` of the link it returns. The link must be **https on `*.opensubtitles.com` or `*.opensubtitles.org`** with no credentials and no port; redirects are followed by hand and each hop must pass the same test; the body is cut at 2 MB while it streams; no key and no token go to the link, and the link is never kept. The credentials, the key and the token only ever go to OpenSubtitles' API host (`api.` or `vip-api.opensubtitles.com`); `base_url` from the login and the `OPENSUBTITLES_REST` setting naming any other host are ignored (the setting is logged as `opensubtitles-rest-setting-ignored`). The answer is the SRT as `text/plain; charset=utf-8` with `Access-Control-Allow-Origin: *`. A refused token (401) is renewed once (a newer one in KV is used before logging in). **`HEAD` never downloads**: it answers 200 with no body for a subtitle already kept and 405 otherwise. Anything else is a **502** with `Cache-Control: no-store` and a short reason in `X-Subfile`: `quota`, `login-failed`, `login-paused`, `busy` (429 or 5xx), `rejected` (406 without a quota: an invalid file id), `download-failed`, `no-link`, `file-failed`, `bad-file`. Logs: `opensubtitles-login-rejected` (with the status), `opensubtitles-login-error`, `opensubtitles-login-bad-answer`, `opensubtitles-download` (with `remaining`, a number), `opensubtitles-quota-out`, `opensubtitles-paused` (19/10/2026: `{ until }`, an ISO time; a download was refused because the day's counter is at 0 or below, so OpenSubtitles was not called; no key, no hash, no file id), `opensubtitles-download-rejected`, `opensubtitles-download-failed`, `opensubtitles-file-failed`, `subtitles-extras-failed`, `subs-kv-failed` (the operation and a fixed label), `subs-kv-slow`. A download that leaves `remaining` at 0 marks the quota out at once, like the 406, and is still served. **The three requests that carry the key, the credentials or the token (the hash search, the login, the download) are made with `redirect: "manual"`: a 3xx is a failure and nothing is sent to the host it names**; the hash search answer is read with a 1.5 MB limit like the others. The user name, the password, the token, the private token and the link are never logged by the Worker and never in an answer (and Cloudflare's own invocation log, which records `<Method> <URL>` of every request, so the private token, the signed `/subfile` links and the hash of a search, is **off**: `[observability.logs] invocation_logs = false`, pinned by a test that reads `wrangler.toml`) (`test/subfile.test.js` scans every answer, log and KV value of eight scenarios for them).

**The quota, and the risk.** A free OpenSubtitles account may download **20 subtitles a day** (documented; 1,000 for a VIP), counted per **distinct file**, reset at **midnight UTC** (21:00 in São Paulo); the same file asked again within 3 hours is not counted again. Each subtitle of this kind opened for the first time costs one. **A binge day can exhaust the 20**: Stremio may fetch the address of the subtitle it picks by itself when a film starts, and these rows are in the exact tier, so a film whose only exact subtitle is one of these spends one the first time it is played (a second play is free: the Worker keeps the file for 30 days). When the quota is out the Worker stops listing the rows (see above) and keeps serving what it holds; a row that was already listed and is opened fails with a 502. Look in the log for `opensubtitles-download` (with `remaining`), `opensubtitles-quota-out` and `opensubtitles-paused`. **Since 19/10/2026 (W5 of the 13/10 plan)** the count of the day is also kept in KV (`os:remaining:<date>`, see "Secrets and the KV binding"): at 0 the Worker does not call OpenSubtitles at all until the reset moment, answers the same 502 `quota` as for a spent quota, and logs `opensubtitles-paused` once for each refused attempt. The number is the `remaining` of the download answer's body (the per-second `x-ratelimit-*` headers are not the day's quota and are not read). `offering()` reads the counter too (today's key and tomorrow's, in the same 300 ms as its other reads) and lists no row while it pauses: `quota:v1` alone ends after 10 minutes when the answer gave no reset moment, while the counter lasts until midnight UTC (found by the security review of 19/10/2026: the rows were listed and each one was a 502). A damaged value in KV pauses for at most a day. Tested in `test/subfile.test.js` with the fake KV; not measured against the real API (the real answer's `reset_time_utc` is documented, not seen in this work).

**Checked live on 13/10/2026** (Paterson, `tt5247022`, hash `1cddc37a1943f1ae`, private address): the listing gave `X-Subtitles-Extras: 2` (two English, labelled at that time "✓ Exact · Paterson.2016.1080p.BluRay.X264-AMIABLE"; now "English ✓ exact"); the first `/subfile` answered 200, `x-subfile: source`, an SRT of 99,079 bytes in UTF-8 (so the real login, `/download` and the link fetched from the Worker all worked), the next one `x-subfile: kv`; in stremio-web (Chrome on Marco's Mac, signed in) the extra was listed first and shown on screen at its SRT time. In that session the file's embedded tracks had not loaded, so it does not show what wins against an embedded English track (the client research says the embedded one does). The same day the first deploy answered `X-Subtitles-Extras: 0` because the hash search cached by the previous version (a plain array, 24 h, in the Cache API) hid the extras: the key became `exact2:` (PR #18), which also showed that the Cache API keeps entries on `workers.dev`. **What was not checked:** no device other than stremio-web in Chrome; whether the terms of use allow a Worker to keep a subtitle for 30 days (the terms page could not be read; the staff said what may not be stored is the *link*); whether a stale token is refused with 500 instead of 401 (the documentation says both); how Stremio, Nuvio and Fusion treat a `text/plain; charset=utf-8` address ending in `.srt`; and **whether an app skips a subtitle whose address answers 502 or lets the player stall on it**. Also not verified: **stremio-web keeps the first entry per id by position** (from the coordinator's research of the same day; I did not read stremio-web's code or test it), so if the first request for a film came **without** a `videoHash` (no extra rows are possible then) and a later one with it, the extras may not appear in that session. The documentation asks developers not to hard-code their own account in an app they distribute; this Worker is Marco's alone and the account is in a secret, never in the repository. Changing the private token makes every row Stremio holds (up to an hour) answer 404 and, worse, makes the whole private addon answer 404 on every device until it is reinstalled (see "The private address").

   Paste the key at the prompt and press Enter. It is stored by Cloudflare and never appears in the repository, in `wrangler.toml` or in any answer; the Worker does not write it in its logs either. (To try it with `wrangler dev`, put the line `OPENSUBTITLES_API_KEY=<the key>` in a file `worker/.dev.vars`; git ignores that file.)

**What the key is used for, and the limits.** (Since 19/10/2026 only for requests under the private address; the public address and the public profiles make no search.) One search per (file hash, title) per 24 hours: `GET https://api.opensubtitles.com/api/v1/subtitles?imdb_id=…&languages=en,pt-br,pt-pt&moviehash=…` with the headers `Api-Key` and `User-Agent: MoodEngine v3.1.0`. Nothing is downloaded through the API on the public address (Stremio downloads the file from the address in the official list), so the download quota (5 a day with no account, 20 a day with a free one, according to OpenSubtitles' help centre) is not touched there. (Marco, 12/10/2026: the private address does download through the API, with his account: see "Subtitles the official list lacks".) I measured the limit of a free consumer with the key on 10/10/2026: **5 requests a second** (`x-ratelimit-limit-second: 5`); I found **no daily cap on searches** in the headers or in the documentation pages I could read (the documentation site is a JavaScript page my tools could only partly read: it confirms the parameters `moviehash`, `imdb_id`, `languages`, `type`, the headers and the response fields; the quotas I could not read there). A Jellyfin plugin's issue tracker quotes 40 requests per 10 seconds per IP for the same API. If the API ever answers 429 or an error, the Worker serves the list without the exact tier and does not ask again for that file for 5 minutes.

**What was confirmed live** (Paterson, `tt5247022`, hash `1cddc37a1943f1ae`, 29 results, HTTP 200): the answer has `total_pages`, `total_count`, `per_page` (50), `page`, `data`; each result has `attributes.moviehash_match`, `attributes.legacy_subtitle_id` and `attributes.files[].file_id`; three results had `moviehash_match: true` and came **first** (two English of the AMIABLE release, one Brazilian Portuguese). The match to the official list is by `legacy_subtitle_id` = the official list's `id`. **`file_id` is not used:** it is a different numbering from the number the official download address ends with (they never agree in the data), and a number that agreed by accident would mark an unrelated subtitle as exact. **Limit of the exact tier:** it can only mark subtitles the official list already contains; of Paterson's three hash matches, only the Brazilian one is in the official list (the two English ones are newer and the list, which has just 12 English subtitles for this film, does not carry them). Bringing REST-only subtitles in would need a download address, which the REST API gives only to a logged-in user. ## When something is down

| What happens | What the Worker does |
|---|---|
| The index is fresh (under 30 min) | answers from the copy in memory |
| The copy is older than 30 min (but under a day) | answers **at once** from it, and refreshes in the background (stale-while-revalidate): the refresh is handed to the execution context's `waitUntil`, which is what lets it finish after the answer went out. Until 14/11/2026 one read did not hand it over: the whole index read by a profile's theme of more than 8 lists (21st century, World cinema, All-time canon), because a local constant in `handler.js` had the same name as the execution context; `test/profiles.test.js` now checks that every store read of every profile catalog request gets the execution context (the v2 slices and option pieces of the old address are not under that check) |
| A new isolate (a cold start) | reads the **Cache API** of the data centre, else the published file; a copy written there by another isolate is used. (Cloudflare documents the Cache API for custom domains; on this `workers.dev` address an entry written by the previous version was still read after a deploy on 13/10/2026, so it does keep entries here, per data centre.) |
| GitHub Pages is unreachable | serves the newest copy it has anywhere, **up to 7 days old**, logs `index-unavailable`, and does not ask again for a minute |
| Nothing at all (or older than 7 days) | catalogs answer `200` with `{"metas": []}` and `Cache-Control: max-age=30` (an empty page is not remembered), the manifest answers `503`; the failure is logged |
| The file is not an index (HTML error page, another schema, other columns) | refused, the good copy stays |
| The fetch of the index takes more than **20 seconds**, or the body is over **16 MB** (13/10/2026; today's `index.json` is 6.579.269 bytes, gzip 2.142.713, measured 13/10/2026 21:05 GMT, so 16 MB is 2,4 times the file; the build refuses an index over 4 MB gzipped, about 12 MB decompressed; at the limit the chunks, the joined copy and the decoded text hold about 64 MB of the isolate's 128 MB, which is why it is not 32 MB) | an ordinary failure of the network: the copy in memory or in the Cache API stays, the source is not asked again for a minute, and the log says `index-fetch-limit` with `reason` `timeout` or `too-large` (next to `index-unavailable`). The time covers the body, and the body is cut as it streams |
